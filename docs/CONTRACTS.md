# Proposed shared contracts, v0

This is the coordinator's initial interface proposal for independent planning. Workers should identify necessary changes in their reports. The consolidated plan will resolve them before implementation begins.

## Service boundaries

- `backend/app/api/`, `backend/app/assistant/`, `backend/app/providers/`, `backend/app/contracts/`: G1.
- `backend/app/retrieval/`, `backend/app/ingestion/`, `data/sops/`: G2.
- `backend/app/inventory/`, `data/inventory/`, inventory migrations: C1.
- `frontend/`: C2.
- `evals/`, `tests/evaluation/`: G3.
- `infra/`, `scripts/`, `.github/`, integration tests and delivery docs: C3.

G1 owns Python dependency declarations and the shared application bootstrap. C2 owns frontend dependencies. Inventory and retrieval migrations must use nonconflicting IDs and be sequenced by the coordinator. No worktree runs schema changes against another worktree's database.

## HTTP boundary

- `POST /api/chat`: `{message, history?}`. Bounded client-supplied conversation history; it is untrusted user context, never a source of fresh inventory facts.
- Returns `{answer, status, citations, inventory_result, clarification, trace_id, data_mode}`.
- `status`: `answered | needs_clarification | insufficient_evidence | temporarily_unavailable`.
- `data_mode`: `synthetic` always in this demo. `inventory_result` and `clarification` can be null.
- `GET /api/sops/{document_id}/sections/{section_id}`: return the original versioned source section used in a citation.
- `GET /api/health`: process liveness; readiness/provider configuration is separately identifiable.
- Nonstreaming first. Validate requests/responses with Pydantic. OpenAPI generates frontend types after the interface is frozen.

## Retrieval boundary

`search_procedures(query, limit=5)` returns passages containing `document_id, version, section_id, title, text, source_uri, score`.

`Citation` contains `document_id, version, section_id, title, quoted_text, source_uri`. Citation IDs are assigned by the server from retrieved passages. Raw model output cannot invent a source path. Internal UI links must resolve the exact version. Only current documents are eligible by default; conflicting current procedures produce an explicit uncertainty state.

## Inventory tools

`lookup_stock(part_query)` returns `ok | ambiguous | not_found | unavailable` with matching canonical part IDs, quantities, unit, and `snapshot_id`/timestamp.

`check_build_readiness(assembly_id, quantity)` accepts a selected canonical assembly ID and a positive integer quantity. Returns a deterministic result containing requested units, readiness, per-component requirements/available/shortage, and data snapshot metadata. Clarify assembly identity before calling this function when a name is ambiguous.

For each component: `required = per_assembly * quantity`; `shortage = max(required - available, 0)`. Readiness requires all components to have known availability and zero shortage. Missing records, empty BOMs, invalid quantities, or unavailable databases cannot yield `ready=true`.

Use typed arguments, parameterized SQL/ORM queries, and read-only runtime database credentials. Seeding/migrations use separate development credentials. There is no free-form SQL tool, component deduction, purchasing, or employer connection.

## Assistant boundary

One bounded tool-calling loop, strict tool allowlist, argument validation, explicit call/time limits, and bounded transient retries. Retrieval content is data, not instructions. Numerical answers derive from structured tool results. Chat history does not authorize new tools. Plain-language answers keep required steps and warnings intact and link to the original procedure.

## Evaluation boundary

Case fields: `id, group_id, split, category, input, expected_status, expected_source_ids, expected_inventory, expected_clarification, notes`.

Keep paraphrases and sibling cases in the same split. Reference expected inventory values are independently specified, not generated by calling the function under test. Separate deterministic component checks, offline transport mocks, and live model runs. Store configuration, corpus/seed versions, commit, and failure records with each run; only live runs support claims about LLM behavior.
